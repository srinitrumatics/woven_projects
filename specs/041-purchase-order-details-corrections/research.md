# Research: Purchase Order Details Page — Corrections

No `NEEDS CLARIFICATION` markers remain in the Technical Context — this document consolidates the findings of four parallel background audits (one per tab) that resolved every open question before planning began.

## Decision: Purchase Order Lines tab requires structural, mapping, and sort fixes

**Rationale**: `POLinesTable.tsx` currently shows a self-referential "Purchase Order" column (a line linking back to its own parent, the same anti-pattern already corrected elsewhere in this PO feature area per spec 031) in place of the requested "Customer Quote Line" position, and is missing "Proposed Product," "Need By Date," "Promise Date," and "Action" entirely. Two further columns ("Open Balance Qty," "Invoice Status") are present but unrequested. Product Name renders as plain text with no linkable ID field mapped. Brand is hardcoded to `undefined` (line 31) and mislabeled "Brand" instead of "Brand Name." "Shipping" is mapped from the parent PO's `Total_Shipping_Charges__c` field instead of the line's own `Shipping_Charges__c` field — confirmed by cross-referencing `app/purchase-orders/[id]/lines/[lineid]/page.tsx:62` and `PODebitMemoLinesTab.tsx:36/130/178`, which both correctly use the unprefixed line-level `Shipping_Charges__c`. None of the three financial fields (Total Cost, Shipping, Line Grand Total) has a `gtherp__`-prefixed fallback, unlike the same fields at the PO-header level (fixed in feature 040). "Line Total Cost" is mislabeled — it should read "Line Grand Total." Tracking Status and Estimated Delivery Date are transposed relative to the requested order. Default sort is `{ key: 'name', direction: 'desc' }`; requested is ASC.

**Alternatives considered**: N/A — every finding was confirmed by direct grep/read against the file and cross-referenced against already-correct sibling conventions in this same PO feature area (`PODebitMemoLinesTab.tsx`, `PORtvLinesTab.tsx`, `POSupplierBillLinesTable.tsx`, all one level deeper at `[lineid]/components/`), so the fix in each case is to match those already-proven-correct patterns rather than invent a new convention.

## Decision: Supplier Bills tab requires the most extensive corrections of the four tabs

**Rationale**: `POSupplierBillsTable.tsx` shows "Supplier Name," "Supplier DBA," and "Supplier Contact" where the request calls for "Ship to Account," "Ship to Location," and "Ship to Contact" — entirely different data, not just a label mismatch. "Proposal #" and "Proposal Name" are missing entirely (no such field exists anywhere in the `SupplierBill` interface). "Action" is missing entirely (no header, no cell). No `isManufacturer` computation or prop exists anywhere in this file — Customer Quote #, Proposal # (once added), and Customer Order # currently render as unconditional hyperlinks with zero account-type gating, unlike the established convention at `app/purchase-orders/page.tsx:184,332-371`. The three financial columns are mislabeled and shifted: the field mapped from `Total_Product_Amount__c` is labeled "Total Cost" (should be "Total Amount"), and the field mapped from `TotalAmount__c` is labeled "Total Amount" (should be "Grand Total") — none has a `gtherp__`-prefixed fallback. Remittance Status color-coding is already correct (via the shared `RemittanceBadge` component). Open Balance has zero color-coding logic at all — the cell renders with static gray text regardless of sign, not merely a wrong-threshold bug but a complete absence of the conditional styling. An extra "Days Outstanding" column exists that isn't requested. Default sort is DESC; requested is ASC. The empty state bypasses the table/headers entirely via an early `return`, unlike the `<tr><td colSpan>` convention used on the PO landing page.

**Alternatives considered**: N/A — every finding was confirmed by direct grep/read; the fix pattern (add `isManufacturer` via `useUserSession`, add `gtherp__` fallbacks, add threshold-based conditional Tailwind classes for Open Balance) mirrors conventions already proven correct on `app/purchase-orders/page.tsx` and the `RemittanceBadge` component already in use on this same file.

## Decision: Serial Number Logs tab requires a tab-bar rename plus three column fixes

**Rationale**: `POTabs.tsx:20` currently labels this tab "Serial Numbers," while the table's own content consistently refers to itself as "Serial Number Logs" (sticky column header, empty-state copy, and `Pagination itemName` prop all already say "Serial Number Logs" or "Serial Number Log"). The tab-bar label is the one place that doesn't match, confirming the request's "rename to match" instruction refers to fixing this specific mismatch. Brand Name is missing entirely — no `Brand_Name__c`/`gtherp__Brand_Name__c` field exists in the `SerialNumberLog` interface, confirmed absent via grep. The established fallback pattern to copy is `app/shipments/[id]/components/SerialNumbersTab.tsx:48` (`raw.Brand_Name__c || raw.gtherp__Brand_Name__c || ""`). Product Name renders as plain text with no product ID mapped — the same sibling file's pattern (`productId: raw.Product__c || ""`, then a `<Link href={\`/products/${log.productId}\`}>`) is the fix to copy. Two further column labels are missing their "#" suffix ("Serial Number" → "Serial Number #," "RMA" → "RMA #"), and "Purchase Order" is missing its "#" suffix too, though its hyperlink is already correctly wired. Default sort is DESC; requested is ASC, matching the sibling shipments tab's already-correct `{ key: 'name', direction: 'asc' }`.

**Alternatives considered**: Renaming the tab-bar label to copy the shipments sibling's exact string ("Serial Numbers Logs," with a grammatically awkward extra "s") — rejected; the correct target is "Serial Number Logs" (singular "Number"), matching this tab's own internal copy exactly, not the sibling's slightly-off label.

## Decision: Returns tab (RTVs and Debit Memos) both need Proposal columns, unconditional PO # links, and an ASC sort fix

**Rationale**: On both `PORTVTable.tsx` and `PODebitMemoTable.tsx`, the Purchase Order # hyperlink is incorrectly wrapped in an `isManufacturer`-gated ternary (rendering plain text for Supplier accounts), when the request and the confirmed convention at `app/purchase-orders/page.tsx:326-330` both require it to always render as a link regardless of account type — this is the opposite of the correct pattern (PO # should be unconditional; Customer Quote #/Proposal #/Customer Order # should be the ones gated, and those are already correctly gated on both sub-tabs). Proposal # and Proposal Name are missing entirely on both sub-tabs. On RTVs, the label "RTV" needs a "#" suffix, "RTV Type" needs relabeling to "Type" and repositioning earlier (to position 3), "RMA Number" needs relabeling to "Supplier RMA Number" and repositioning to last, and three unrequested columns (Supplier Name, Supplier Contact, Approval Date) need removal. On Debit Memos, "Debit Memo" needs a "#" suffix, "Expiration Date" (`gtherp__Expiration_Date__c`, a field already confirmed legitimate and in use elsewhere — `app/quotes/types.ts:25`, on Quote Credit Memos) is missing entirely, and five unrequested columns (Supplier Bill, Supplier Credit Memo, Debit to Account, Debit to Contact, Approval Date) need removal. Both sub-tabs default-sort DESC; the request explicitly and separately calls out "Returns Tab Sort Order (RTVs, Debit Memos)" as its own line item distinct from the general ASC requirement, and code inspection confirms this suspicion was correct — both are currently DESC and must change to ASC.

**Alternatives considered**: Treating the request's duplicated "Debit Memo #" (listed twice in the Debit Memos column list — once first, once again after Status) as a real, distinct second field — rejected after confirming via grep across this codebase (including the analogous Quote-level Debit Memo table and its `QuoteDebitMemo` interface) that no second, different "Debit Memo #"-style field exists anywhere; this is documented as an assumed authoring duplication, and only one Debit Memo # column is specified (consistent with how every other tab's own-record-name column appears exactly once).

## Decision: Field-availability risk for newly-added columns is accepted, not blocking

**Rationale**: Since this page's data comes from a generic Salesforce Apex REST proxy with no in-repo SOQL/field list (`lib/purchase-order-service.ts:34-87`), it cannot be statically confirmed that every newly-requested field (Brand Name on Serial Number Logs; Proposal #/Name on Supplier Bills, RTVs, Debit Memos; Expiration Date on Debit Memos) is actually returned for Purchase-Order-context records specifically, even though the same field names are confirmed to exist and work on sibling objects elsewhere in the portal. Given every other corrected field in this portal's history has turned out to be available once the frontend mapping was added (the underlying Apex proxy is generic and typically returns whatever fields exist on the record), and the null-dash convention means an absent field degrades gracefully to "-" rather than breaking the page, this risk is accepted rather than treated as a blocking clarification.

**Alternatives considered**: Marking field availability as a `[NEEDS CLARIFICATION]` item requiring the user to confirm against a live org before writing the spec — rejected as disproportionate; the existing graceful-degradation convention (null-dash) already handles the failure mode safely, and this is consistent with how every other new-column feature in this series (033 onward) has proceeded without live-org verification at spec time.
