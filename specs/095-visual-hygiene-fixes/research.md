# Research: Visual Hygiene Fixes

All findings below are grounded in a direct read of every affected file before planning. No `NEEDS CLARIFICATION` markers remain in the spec.

## 1. Order Line Detail's stepper unification

**Decision**: Change the desktop-table stepper buttons in `app/orders/[id]/lines/[lineId]/components/OrderDetailsTable.tsx` (lines 141-153) from `"w-6 h-6 flex items-center justify-center rounded border shadow-sm bg-gray-100 dark:bg-gray-700 hover:bg-gray-200 dark:hover:bg-gray-600 border border-gray-200 dark:border-gray-600"` to `"w-6 h-6 flex items-center justify-center rounded border shadow-sm transition-colors text-lg bg-white dark:bg-gray-600 border-gray-200 dark:border-gray-500 hover:bg-gray-50 dark:hover:bg-gray-500 text-gray-900 dark:text-white"` — i.e. the mobile version's exact color/border/hover/text classes (lines 72-84), keeping only the desktop-appropriate `w-6 h-6` size instead of mobile's `w-8 h-8`.

**Rationale**: Confirmed via full read that both steppers share identical `onClick={decrementQty}`/`onClick={incrementQty}` handlers and structure — only the `className` strings diverge in color scheme (mobile: white/gray-600 background; desktop: gray-100/gray-700 background) and size (`w-8 h-8` vs `w-6 h-6`). The size difference serves a legitimate purpose (larger touch targets on the mobile card layout vs. denser table rows on desktop) and is preserved; only the color/border/hover/text treatment is unified.

**Alternatives considered**: Extracting a shared `QtyStepper` sub-component with a `size` prop — rejected as premature abstraction (Constitution Principle V, YAGNI); this is the only file in the entire codebase with this stepper pattern (confirmed via investigation — the audit's claim of "3 files" was stale, and the only other similar-looking stepper found, in `ProductInfoCard.tsx`, belongs to a different module entirely and is out of scope), so a new shared component would have exactly one export point using it twice, not a genuine reuse case.

Replace "Purchase Orders" (line 74-78) with the Heroicons `ClipboardDocumentListIcon` outline path (`M9 12h3.75M9 15h3.75M9 18h3.75m3 .75H18a2.25 2.25 0 002.25-2.25V6.108c0-1.135-.845-2.098-1.976-2.192a48.424 48.424 0 00-1.123-.08m-5.801 0c-.065.21-.1.433-.1.664 0 .414.336.75.75.75h4.5a.75.75 0 00.75-.75 2.25 2.25 0 00-.1-.664m-5.8 0A2.251 2.251 0 0113.5 2.25H15c1.012 0 1.867.668 2.15 1.586m-5.8 0c-.376.023-.75.05-1.124.08C9.095 4.014 8.25 4.977 8.25 6.108V8.25m0 0H4.875c-.621 0-1.125.504-1.125 1.125v11.25c0 .621.504 1.125 1.125 1.125h9.75c.621 0 1.125-.504 1.125-1.125V9.375c0-.621-.504-1.125-1.125-1.125H8.25zM6.75 12h.008v.008H6.75V12zm0 3h.008v.008H6.75V15zm0 3h.008v.008H6.75V18z`). **Alternatives considered**: Changing "Catalog"/"Orders" instead of "My Inventory"/"Purchase Orders" — rejected; no strong reason to prefer one member of each duplicate pair over the other, so the choice was made on which replacement icon better fits its *own* concept (ArchiveBox for inventory storage, ClipboardDocumentList for a purchase-order document) rather than arbitrarily.

## 3. Shared Breadcrumb component

**Decision**: Build `components/ui/Breadcrumb.tsx` with `{ items: { label: string; href?: string }[], className? }`. Non-last items with an `href` render as `next/link`; the item with no `href` (or the implicit last item) renders as plain text. Migrate `ProposalHeader.tsx`, `app/proposals/[id]/summary/page.tsx`, and `app/proposals/[id]/lines/[lineid]/page.tsx` onto it. `ProposalHeader.tsx` gains a new `id` prop (its parent, `app/proposals/[id]/page.tsx`, already has `id` in scope via `const { id } = use(params)` at line 50 but doesn't currently pass it down) so its "Proposal Details" segment can link to `/proposals/${id}`, matching the identical pattern already used correctly by the other 2 pages.

**Rationale**: Confirmed via full read that the Summary and Line Detail pages already implement a near-byte-identical, correctly-working `<button onClick={() => router.push(...)}>`-based breadcrumb — using `next/link` instead of a click-handler-driven `router.push` in the new shared component is a strict improvement (real anchor semantics, no `useRouter` dependency needed in either the shared component or eventually its callers) while preserving the exact same visual behavior. `ProposalHeader.tsx`'s current breadcrumb has 2 static `<span>` segments where the equivalent segments are real links on the other 2 pages — confirmed this is a genuine functional gap (its "Proposal Details" segment even has a `hover:` style already applied, suggesting it was intended to be clickable and never finished), not just a style difference.

**Alternatives considered**: Making `ProposalHeader.tsx`'s "Proposal Details" breadcrumb segment plain (non-clickable) text instead of adding the `id` prop, since it's already on the Proposal Detail page (clicking it would just navigate to the same URL) — rejected; FR-008 explicitly requires this segment to become clickable and navigate correctly, matching the shape of the other two working implementations, and a self-linking breadcrumb segment (common in many apps as a "return to top of this section" affordance) is a defensible pattern that costs nothing to support correctly.

## 4. Filter pills onto shared `Tabs`

**Decision**: Migrate `app/shipments/page.tsx` (lines 444-467), `app/inventory/page.tsx` (lines 574-587), and `app/admin/authorize-locations/[id]/delivery-windows/page.tsx` (lines 278-292) onto `components/ui/Tabs.tsx`, mapping each page's existing filter list to `Tabs`' `TabItem[]` shape (`{key, label}` — `count`/`disabled` unused, since none of the 3 pages currently show counts on their pills), each page's existing active-filter state as `activeKey`, and each page's existing click handler (`setActiveTab`/`handleCardClick`) as `onChange`.

**Rationale**: Confirmed via full read that `Tabs.tsx`'s existing `{tabs, activeKey, onChange, className}` API requires no new props to fit any of the 3 pages — Shipments' dynamic `uniqueStatuses.map(...)` list, Inventory's fixed `["All", "On Hold", "Put-Away", "Average Aged"]` list, and Delivery Windows' fixed `['All', 'Active', 'Inactive']` list all reduce to a simple `label`-only `TabItem[]` array. This is the smallest possible fix — a rendering swap with zero new component API surface — for 3 pages that already independently reimplement the exact same active/inactive-pill concept `Tabs.tsx` already correctly solves.

**Alternatives considered**: Building a page-specific "filter pill" variant of `Tabs` instead of the exact same component used for detail-page tab bars — rejected; the audit's own framing (§17.9) explicitly calls for reusing `Tabs.tsx` itself ("Replace with `<Tabs>`"), and confirmed via source read that its existing visual output (`bg-primary`/`bg-primary-light` pill) is what these 3 pages should have looked like all along, not a new third visual variant.
