# Research: Button Color Consistency

All findings below are grounded in a direct read of every affected file before planning. No `NEEDS CLARIFICATION` markers remain in the spec.

## 1. "Add to Order" color fix (US1)

**Decision**: Change `app/products/[id]/components/ProductInfoCard.tsx:93` from `bg-blue-600 hover:bg-blue-700` to `bg-primary hover:bg-primary-dark`. Change `app/products/[id]/components/AddToOrderModal.tsx:216` and `:225` from `bg-blue-600 hover:bg-blue-700 ... shadow-lg shadow-blue-500/20` to `bg-primary hover:bg-primary-dark ... shadow-lg` (dropping the blue-tinted shadow, since no other `bg-primary` button anywhere in the codebase pairs with a color-tinted shadow — confirmed via grep, every `bg-primary` button uses a plain `shadow-sm`/`shadow-md`/`shadow-lg`). No other classes on any of the 3 buttons change — disabled state (`disabled:bg-gray-400 disabled:cursor-not-allowed`), sizing, radius, and font-weight are untouched.

**Rationale**: Confirmed via direct read that the Products catalog's own "Add to Order" quick-button (`app/products/ProductClientPage.tsx:597`) already uses `bg-primary hover:bg-primary-dark` — the correct, majority-intended brand token per `tailwind.config.ts`. The other 2 call sites for the identical semantic action use `bg-blue-600 hover:bg-blue-700`, an off-brand color with no basis in the design system. Converging on the catalog's already-correct token is the smaller, more targeted fix than inventing a new color.

**Alternatives considered**: Changing the catalog's button to `blue-600` instead (majority-vote-by-count, since 2 of 3 sites use blue) — rejected; `blue-600` doesn't exist anywhere in `tailwind.config.ts`'s palette, while `primary`/`primary-dark` are the app's actual documented brand tokens (per `CLAUDE.md`) — correctness, not vote count, decides convergence direction.

## 2. Admin Login token alignment (US2)

**Decision**: In `app/(admin-portal)/admin-login/page.tsx`, change: (a) the icon bubble (line 53) from `bg-gradient-to-br from-blue-500 to-indigo-600` to `bg-gradient-to-br from-[var(--primary)] to-[var(--primary-dark)]` — reusing the exact gradient token pair already present on `/signin`'s own right-side panel (`components/SignInForm.tsx:233`); (b) both input fields (lines 77, 92) from `rounded-2xl ... focus:ring-blue-500/40 focus:border-blue-500` to `rounded-md ... focus:ring-[var(--primary)] focus:border-transparent`, matching `/signin`'s input treatment (`SignInForm.tsx:154,172`) exactly; (c) the corresponding focus-within icon colors (lines 71, 86) from `group-focus-within:text-blue-500` to `group-focus-within:text-[var(--primary)]`; (d) the submit button (line 101) from `bg-gradient-to-r from-blue-600 to-indigo-600 hover:from-blue-500 hover:to-indigo-500` to `bg-[var(--primary)] hover:bg-[var(--primary-dark)]`, matching `/signin`'s own solid-color submit button (`SignInForm.tsx:213`) rather than keeping a gradient nothing else in the app's auth flow uses.

**Rationale**: `/signin` is the reference pattern for what "this app's login screen" should look like, color-wise — its inputs (`rounded-md`, `focus:ring-[var(--primary)]`) and submit button (`bg-[var(--primary)] hover:bg-[var(--primary-dark)]`) are both confirmed via direct read. Admin Login's blue/indigo gradient and `rounded-2xl` inputs have no basis in `tailwind.config.ts` and make the two login screens read as unrelated products despite performing the identical job.

**Alternatives considered**: Rebuilding Admin Login's overall shell (centered card → split-screen, matching `/signin`'s layout) — explicitly rejected per FR-006/FR-007; the two auth systems are intentionally structurally independent per `CLAUDE.md`'s architecture section, and this feature only corrects color/shape *tokens*, not layout. Also considered: changing the submit button's shape from `rounded-2xl` to `rounded-full` (matching `/signin`'s button exactly) — rejected as out of the spec's named scope (FR-005 only names the icon bubble and input fields for shape correction, not the button); changing the button's *color* alone (FR-004) already resolves the primary visible mismatch without touching more surface than specified. Also considered: recoloring the decorative background blur blobs (`bg-blue-100`/`bg-indigo-100`, lines 47-48) — left untouched; these are low-opacity ambient decoration never named in the spec's functional requirements or acceptance scenarios, and touching them would be scope creep beyond the 2 confirmed mismatches this feature targets.

## 3. Scope boundary — what's explicitly NOT touched

**Decision**: Admin Login's overall page layout (centered single-card shell, form structure, `/api/auth/admin/login` auth logic) is left completely untouched. Orders' "Cancel"/"Save Draft" (outlined) vs. OrderHeader's "Clone" (filled-gray) button-style difference is left untouched.

**Rationale**: A dedicated investigation (prior to this spec's authoring) confirmed the Orders button-style difference is a reasonable secondary-action-tier distinction between two different UI regions (a sticky bottom action bar vs. a page header), not a genuine same-tier mismatch — it doesn't meet the bar this feature's other 2 fixes do (identical semantic action, provably drifted color). Admin Login's layout independence from `/signin` is an intentional architectural decision (two separate auth systems), not a defect.

**Alternatives considered**: Including the Orders button-style difference as a 3rd user story — rejected; unlike US1/US2, no single semantic action renders in two different colors here, just two different secondary-action UI regions using two different (individually reasonable) conventions.
