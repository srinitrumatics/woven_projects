# Research: Shipping Manifest Details Page — Corrections

No `NEEDS CLARIFICATION` markers remain in the Technical Context — this feature has no unresolved unknowns. This document records the audit findings that resolved every open question before planning began.

## Decision: Fix the Customer Quote Line hyperlink by capturing the parent quote ID separately

**Rationale**: `app/shipments/[id]/components/ShipmentLinesTab.tsx:86-87` currently maps `customerQuoteId: raw.Customer_Quote_Line__c` and `customerQuoteLineId: raw.Customer_Quote_Line__c` — both from the *same* field, the quote line's own ID. The render at line 238 then does `<Link href={\`/quotes/${line.customerQuoteLineId}\`}>`, passing a quote-line ID into a route (`app/quotes/[id]/page.tsx:37,174`) that is confirmed to expect a top-level Quote (`Customer_Quote__c`) ID, not a Quote Line ID — every populated Customer Quote Line click today lands on a broken/incorrect page. The already-correct sibling component `app/purchase-orders/[id]/components/POLinesTable.tsx:45-46,139` demonstrates the intended convention: capture `customerQuoteId: line.Customer_Quote__c` and `customerQuoteLineId: line.Customer_Quote_Line__c` as two separate fields, then route to `href={\`/quotes/${line.customerQuoteId}/lines/${line.customerQuoteLineId}\`}` — the existing nested route `app/quotes/[id]/lines/[lineid]/page.tsx` confirms this pattern is already supported and working elsewhere in the portal.

**Alternatives considered**: Routing to `/quotes/{lineId}` alone (current broken behavior) — rejected, produces an incorrect/broken page. Making the column non-hyperlinked plain text — rejected, contradicts the explicit request that Customer Quote Line be a hyperlink to its record page, and the correct nested route already exists and works elsewhere.

## Decision: Fix Inventory Positions tab's "Location" to fall back through `Location` first

**Rationale**: `app/shipments/[id]/components/InventoryTab.tsx:63` currently sources `inventoryLocation: raw.Inventory_Location_Name || ""`. The Inventory Landing Page's own detail view (`app/inventory/[id]/page.tsx:65-66,225,255`) does no field mapping at all — it renders `item.Location` directly, a single raw field literally named `Location`. These are two different field names with no overlap, so an inventory position's Location value shown on the Shipping Manifest Details page's Inventory Positions tab does not match the same position's Location value on the Inventory Landing Page, contradicting the explicit request ("RBLP - Use same as Inventory Landing Page"). A third, unrelated convention (`gtherp__Inventory_Location__c || Inventory_Location_Name || Inventory_Location__c`) exists in a sibling file (`app/shipments/[id]/lines/[lineid]/components/InventoryTab.tsx:60`) but is out of scope for this feature (a different page, not part of this request) and does not resolve the mismatch either.

**Alternatives considered**: Changing the Inventory Landing Page to match the Shipping Manifest tab's field instead — rejected, the request explicitly directs this tab to match the landing page's convention, not the reverse, and the landing page's convention (`Location`) is the one already relied upon in two other files (`app/inventory/page.tsx`, `app/inventory/[id]/page.tsx`). Simplest correct fix: fall back through `raw.Location` first, keeping `raw.Inventory_Location_Name` as a secondary fallback in case the field name differs slightly between the two underlying API responses (shipment inventory-position payload vs. inventory landing payload) — preserves existing behavior for any records where `Location` happens to be absent but `Inventory_Location_Name` is populated, while making the primary path match the landing page exactly for the common case.

## Decision: Everything else is verification-only, zero further code changes

**Rationale**: A background audit agent directly inspected all three tab components plus the tab-bar wiring (`ShipmentTabs.tsx`, `page.tsx`) against both the prior spec (`specs/027-shipping-manifest-details-corrections/spec.md`) and this request's exact column lists. Confirmed already correct: column order/labels on all three tabs; Inventory Positions tab reachability (already added by the prior 027 pass); Brand Name mappings on all three tabs (`Brand_Name__c || gtherp__Brand_Name__c`); all six Box dimension mappings on the Shipping Manifest Lines tab (dual-namespace fallback, exact requested API names); Proposed Product and Product Name hyperlinks on the Shipping Manifest Lines tab; Product Name hyperlink on the Inventory Positions tab; Product Name and Shipping Manifest # hyperlinks on the Serial Number Logs tab; sticky first column, full-text single-line headers (`truncate={false}`), `Pagination` (10/page), and ascending default sort (`{key:'name', direction:'asc'}`) on all three tabs.

**Alternatives considered**: Treating the full request as corrective work by default was rejected because it would introduce unnecessary code churn on tabs/columns confirmed to already be correct — violating Constitution Principle V (Simplicity & Phase-Driven Scope, "No speculative rework").

## Out of scope: two minor cosmetic notes surfaced by the audit

**Rationale**: (1) The Action `<th>` on the Shipping Manifest Lines tab lacks an explicit no-wrap class, unlike every `SortableHeader`; low risk given its single short label and fixed 80px width, and not part of the user's explicit request. (2) The tab-bar button label reads "Serial Numbers Logs" (plural) while the request's tab name is "Serial Number Logs" (singular) — this is the tab-bar button text, not an in-table column header, so it falls outside the strict FR list for this feature. Both are documented here for visibility but intentionally left uncorrected since they were not part of the user's request; they can be raised as a follow-up if desired.
