# Research: Purchase Order Landing Page — Required Corrections

No `NEEDS CLARIFICATION` markers remain in the Technical Context — this feature has no unresolved unknowns. This document records the audit findings that resolved every open question before planning began.

## Decision: Add dual-namespace fallback to Total Cost, Shipping, and Grand Total

**Rationale**: `app/purchase-orders/page.tsx:85-87` currently maps `productCost: p.Total_Product_Cost__c || 0`, `shippingCost: p.Total_Shipping_Charges__c || 0`, `totalCost: p.Total_Cost__c || 0` — checking only the unprefixed field name. This request explicitly cites the namespaced API names `gtherp__Total_Product_Cost__c`, `gtherp__Total_Shipping_Charges__c`, and `gtherp__Total_Cost__c`. The audit confirmed this diverges from the dual-namespace fallback convention already established and working elsewhere in this portal: Box dimension fields on the Shipments landing page (`app/shipments/page.tsx:86-91`, `field__c ?? gtherp__field__c`), Brand Name across many pages (`Brand_Name__c || gtherp__Brand_Name__c`), and Ship/Delivered dates on Shipments (`app/shipments/page.tsx:93,96`). Adding the same fallback here ensures a purchase order whose cost data is only populated under the namespaced field still displays correctly instead of showing a blank/zero figure.

**Alternatives considered**: Leaving the fields as unprefixed-only, on the theory that the backend Apex REST endpoint for this specific object always strips the namespace — considered, since the audit noted this was pre-existing and possibly intentional. Rejected as the primary approach because the user's request explicitly names the `gtherp__`-prefixed API names, which is the strongest signal available that the namespaced field is the one that should be checked (at minimum as a fallback), and adding the fallback is a strict improvement with zero risk of regressing the case where the unprefixed field is already populated (it remains the primary source).

## Decision: Everything else is verification-only, zero further code changes

**Rationale**: A background audit agent directly inspected `app/purchase-orders/page.tsx` against both the prior spec (`specs/030-purchase-order-landing-corrections/spec.md`) and this request's exact 26-column list. Confirmed already correct: column order/labels; Purchase Order # hyperlink and sticky first column; Customer Quote #/Proposal #/Customer Order # hyperlink gating using the portal-wide `isManufacturer`-style convention (`['Supplier', 'Manufacturer', 'Manufacturer Rep', 'Logistics Partner']`, byte-identical to ~30 other files in this codebase); Proposal #/Proposal Name as distinct columns; Ship to Contact, Drop Ship, Payment Terms, all four date fields, tracking, and delivery-date columns; full-text single-line headers (`truncate={false}`); `Pagination` (10/page); default sort DESC by the purchase order's own record name; and a `colSpan={26}` empty-state row that correctly matches the actual column count — no off-by-one bug, unlike feature 036's Inventory landing page.

**Alternatives considered**: Treating the full request as corrective work by default was rejected because it would introduce unnecessary code churn on columns/behavior confirmed to already be correct — violating Constitution Principle V (Simplicity & Phase-Driven Scope, "No speculative rework").
